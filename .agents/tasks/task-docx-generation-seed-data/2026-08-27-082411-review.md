# Seed data pipeline and DOCX generation for Form I Mathematics

This change adds three tightly coupled pieces: a seed script that populates the database with the entire Form I Mathematics syllabus (3 topics, 5 sub-topics, 175 periods) and a 2026 academic calendar; two python-docx writer services that generate Scheme of Work and Lesson Plan `.docx` files matching the sample document formats; and API endpoints (`GET .../docx`) that stream those documents. A runner script ties the pieces together and commits example output to `examples/`. The approach uses TestClient as an internal caller to exercise the real API during seeding, then reuses the same app for docx endpoints.

Watch for: the lesson plan endpoint generates all 175 plans in a single synchronous request with repeated DB queries per week (confirmed); the stages table in lesson plans uses hard-coded generic content that doesn't vary meaningfully by topic (confirmed); the `generate_examples.py` script deletes the production database file at the module level before imports, which will destroy data if accidentally run against a non-fresh environment (confirmed).

**Verdict**: APPROVED

## High-level view

The seed script calls the app's own REST endpoints via TestClient, keeping seed data validated against the same schemas the API enforces. This couples the seed tightly to the current API contract — any endpoint signature change will break the seed.

The DOCX writers translate `SchemeOfWorkResponse` and ORM-level `AllocationAssignment`/`LessonPlan` objects into python-docx documents. The scheme writer injects midterm/terminal break rows at heuristic midpoints based on entry count, not calendar metadata — a potential positioning error if allocation produces uneven entry distributions.

The lesson plan docx endpoint iterates all teaching weeks and regenerates/retrieves plans for each one inside the request handler, committing `LessonPlan` rows to the DB as a side effect of a GET request. For the current dataset this is tolerable, but it violates HTTP GET semantics and leaves partial commits on failure.

Tests cover both endpoints with 14 new tests. Not tested: seed script correctness, midterm row positioning accuracy, behaviour when allocation hasn't been run, or sub-topics with zero objectives.

<summary>Issues (5)</summary>

1. **GET endpoint with DB write side-effect** — The lesson plan docx endpoint calls `generate_lesson_plans_for_week` which inserts `LessonPlan` rows and commits. A GET should be idempotent; move plan generation to a POST or pre-generate during allocation.
2. **Single-request N+1 loop for 175 plans** — The docx endpoint loops through all 35 teaching weeks issuing separate queries per week. For this dataset it's ~35 queries; consider batching or pre-fetching assignments in one query.
3. **`generate_examples.py` deletes DB at import time** — `os.remove(DB_PATH)` executes unconditionally at module top-level before any guard. If imported or run accidentally in a non-development context, data is lost.
4. **Static lesson plan stage content** — The stages table (Introduction, Competence Development, Design, Realisation) fills in the same generic text for all 175 lesson plans, only substituting the objective into the Competence Development cell. The produced documents will be repetitive and unlikely to match real teacher expectations.
5. **Midterm row insertion heuristic may misfire** — The scheme writer inserts midterm break rows at `(term_total // 2) + 1` position, but term-break boundaries are tracked by entry count not by week metadata. If allocation produces uneven entry counts per week, midterm rows could appear at unexpected positions.

## DOCX Scheme Writer — midterm row heuristic

The midterm insertion logic groups scheme entries by term and inserts a "MID-TERM ASSESSMENT" + "MID-TERM BREAK" pair when the entry counter reaches `(term_total // 2) + 1`. The scheme response orders entries by week, and a single sub-topic can span multiple weeks (split assignments). If Term 1 has 15 entries and the midterm break should logically appear after week 4, but entry 8 (the threshold) lands at week 6, the break row appears in the wrong place. A safer approach would be to check the `week_number` against the calendar's examination weeks that already carry the correct dates and classification.

The `_derive_month` helper extracts month names from week label strings ("March Week 1" → "MARCH"). This is fragile if label formatting changes, though it's consistent with the seed's current convention.

## Lesson plan endpoint — side-effecting GET and partial commits

`GET /api/lesson-plan/{syllabus_id}/{calendar_id}/docx` loops through all teaching weeks, calling `generate_lesson_plans_for_week` for each. That service function creates `LessonPlan` rows and calls `db.commit()` per week if plans don't already exist:

```python
# lesson_plan_generator.py, line ~100
db.add(lesson_plan)
# ...
db.commit()  # commits all plans for this week
```

If week 20 fails, weeks 1–19 are already committed. The endpoint returns 500 but the DB holds partial state. On retry the endpoint will skip already-committed weeks and succeed, so it's self-healing — but the intermediate state is surprising.

## Static stages table content

The lesson plan docx writer produces a "Teaching and Learning Process" table with four stages. The teaching/learning activities are hard-coded:

- Introduction: "Displaying pictures on manila sheet. Asking students some questions about today's lesson."
- Competence Development: inserts the objective text in a generic frame
- Design: "Ask students in groups to name and explain different things they have learnt"
- Realisation: "Ask each student to show and give examples of what she or he has learnt"

For 175 lesson plans spanning "basic concepts of Mathematics" through "coordinate geometry" and "algebra", every plan reads identically except for the objective substitution. The README describes the output as example documents, but "Displaying pictures on manila sheet" for a coordinate geometry lesson will look wrong to anyone reviewing the output.

## `generate_examples.py` — unconditional DB deletion

```python
DB_PATH = PROJECT_ROOT / "sow_generator.db"
if DB_PATH.exists():
    os.remove(DB_PATH)
    print(f"Removed existing database: {DB_PATH.name}")
```

This runs at module top-level, before any `if __name__` guard. If this module is imported (in a future test or refactored runner), it deletes the database as a side effect of import. Moving the deletion inside `generate_examples()` is the fix.

## Test coverage gaps

Not tested: seed script data correctness (period totals, calendar structure, allocation completeness); midterm row positioning in the scheme docx; behaviour when allocation hasn't been run (the test helper always allocates); sub-topics with zero objectives (the `_get_objective_for_period` function falls back to `sub_topic.title` but this path isn't exercised); the `_derive_month` fallback for labels that don't contain a month name.

## `.gitignore` relaxation

The change from `*.db` to `sow_generator.db` means any other `.db` file created in the repo will be tracked. If the project later produces test or migration databases with different names, they'll appear in git status.
