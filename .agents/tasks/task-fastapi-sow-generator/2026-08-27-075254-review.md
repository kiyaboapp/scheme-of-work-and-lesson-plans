# FastAPI scheme-of-work and lesson-plan generator

A greenfield FastAPI application with SQLite that ingests structured syllabus and calendar JSON, stores it in a relational model, allocates sub-topics to teaching weeks via greedy bin-packing, then exposes endpoints for scheme-of-work and per-period lesson-plan generation. The domain model is well-shaped and the allocation algorithm is deterministic and tested. Watch for: repeated allocation without idempotency creates duplicate assignments (confirmed), lesson-plan date derivation assumes one period = one calendar day which breaks for multi-period days (confirmed), and scheme/lesson generators use hardcoded fallback strings that will need data-driven replacement (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The data model faithfully mirrors the Tanzania O-Level syllabus hierarchy (Syllabus → Topic → SubTopic → Objective) and the academic calendar (CalendarData → Term → Week), with a TextbookEntry sidecar ready for future enrichment. Ingestion endpoints are straightforward CRUD that stores deeply nested JSON in a single transaction. The design decision to model everything relationally rather than as document blobs is the right one for a system that needs to cross-reference sub-topics with weeks.

The allocation engine is a single-pass greedy algorithm that walks sub-topics in syllabus order and fills weeks sequentially, splitting a sub-topic across weeks when it overflows. The critical gap is that calling POST `/api/allocate` multiple times for the same syllabus/calendar pair appends duplicate assignments without clearing the previous run, producing corrupted data on the second call.

Lesson-plan generation is a write-through cache: it creates `LessonPlan` rows on first request and returns existing ones on subsequent calls. The date calculation adds `period_number - 1` days to the week's `start_date`, which maps period 1 to Monday, period 2 to Tuesday, etc. This is wrong for any schedule with more than one math period per day — a common scenario in Tanzanian secondary schools where subjects get 5–7 periods across 5 days.

Scheme and lesson-plan generators fall back to hardcoded strings for teaching methods, resources, and references when textbook entries are absent. These will need to be driven by data (or at minimum configurable) before real use, but they don't block the system from functioning.

<details>
<summary>Issues (5)</summary>

1. **Duplicate allocations on re-run** — POST `/api/allocate` appends new assignments without deleting the previous allocation for the same syllabus/calendar pair. Add a delete-before-insert or upsert guard.
2. **Lesson-plan date off-by-one-day-per-period** — `start_date + timedelta(days=period_number - 1)` maps each period to a different calendar day. For multi-period-per-day schedules this is incorrect. Derive date from `(period_number - 1) // periods_per_day` or store actual period-to-date mappings.
3. **Hardcoded teaching methods and references** — `scheme_generator.py` returns a fixed string for `teaching_methods` and `references` regardless of syllabus content. Wire these to the `competences` JSON or a separate methods table.
4. **No foreign-key validation on textbook POST** — `POST /api/textbook` accepts any `sub_topic_id` without checking it exists, which will succeed at the SQLAlchemy level (SQLite doesn't enforce FK by default) but produce orphaned rows.
5. **SQLite FK enforcement not enabled** — The engine is created without `PRAGMA foreign_keys = ON`, so referential integrity is not enforced at the database level.

## Allocation idempotency gap

`run_allocation` in `app/services/allocation.py` creates `AllocationAssignment` rows and commits them. The POST `/api/allocate` endpoint calls this function without first checking whether an allocation already exists for the given `(syllabus_id, calendar_id)` pair. A second call doubles the assignment count. This is confirmed at line 108 of `allocation.py`:

```python
db.add_all(all_assignments)
db.commit()
```

There is no preceding `db.query(AllocationAssignment).filter(...).delete()`. The GET endpoint at `/api/allocation/{syllabus_id}/{calendar_id}` will then return the union of both runs, which breaks the scheme generator (it iterates all matching rows).

Fix: delete existing assignments for the pair at the top of `run_allocation`, or reject the request with 409 if assignments already exist and require a DELETE endpoint to clear them first.

## Period-to-date mapping in lesson plans

`lesson_plan_generator.py` line 101:

```python
plan_date = week.start_date + timedelta(days=p - 1)
```

`p` here is the absolute period number within the week (1-based, from `first_period` to `last_period`). With a `period_budget` of 5 and a 5-day school week this happens to work — each day gets exactly one math period. But the Tanzania curriculum allocates 7 periods per week for Form 1 Mathematics, meaning some days have two periods. Under that real-world constraint period 6 would land on Saturday and period 7 on Sunday.

The model doesn't capture how periods distribute across weekdays. This is a design limitation rather than a bug in the current test suite (tests use budget=5), but it will produce incorrect dates with real data.

## Hardcoded scheme outputs

`scheme_generator.py` line 89:

```python
teaching_methods="Presentations, Problem solving, Practical work, Research, Group discussion",
```

And line 91:

```python
references="TIE(2023), Basic Mathematics for Secondary Schools Book 1, TIE-DSM",
```

These are invariant across all sub-topics regardless of the competences, subject matter, or textbook data stored in the database. The `competences` JSON field on `SubTopic` is never read by the scheme generator. This means the scheme of work output is structurally correct but content-generic.

## SQLite foreign-key enforcement and textbook validation

SQLite does not enforce foreign keys unless `PRAGMA foreign_keys = ON` is issued on each connection. The engine in `database.py` does not set this pragma via an event listener. Combined with the textbook POST endpoint accepting arbitrary `sub_topic_id` values without a query to verify existence, it's possible to insert textbook entries referencing non-existent sub-topics. The entries will persist but produce no effect (no join will find them). Adding:

```python
from sqlalchemy import event
event.listen(engine, "connect", lambda conn, _: conn.execute(text("PRAGMA foreign_keys=ON")))
```

would catch invalid references at insert time.

## Test coverage assessment

The test suite (32 tests) covers the happy path through the full pipeline: ingestion, allocation, scheme retrieval, and lesson-plan retrieval. It verifies splitting, budget enforcement, and ordering. Not tested: duplicate allocation behavior, invalid foreign keys on textbook entries, error paths when syllabus has zero sub-topics, concurrent requests, and the effect of re-running allocation after data changes. The absence of a duplicate-allocation test means the idempotency bug was not caught.
